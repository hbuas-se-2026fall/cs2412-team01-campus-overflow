# ADR-011：禁用账号后删除全部服务端会话，实现立即下线

**状态**：已接受 ｜ **驱动特征**：安全性 ｜ **相关场景**：PB-40 / T4-02（指导书 6.6.1）

## 背景

`id_user.status` 改为 `DISABLED` 只影响**下一次登录**。已经登录的浏览器会话仍留在 Redis 里，
要等 `spring.session.timeout`（`application.yml` 中为 `30m`）自然过期才会失效 ——
这意味着一个被禁用的违规账号还能继续使用半小时，不满足 T4-02「使其立即下线」的要求。

## 决策

禁用账号时，在同一个用例里删除该主体名下的**全部**会话：

| 环节 | 落点 | 说明 |
| :-- | :-- | :-- |
| 端口 | `SessionRevoker.revokeAll(username) → int`（`co-identity-application`） | 只以「主体名」为参数，不把 Spring Session 的类型泄漏到应用层，便于测试替身 |
| 适配器 | `SpringSessionRevoker`（`co-bootstrap/security`） | `FindByIndexNameSessionRepository.findByPrincipalName(username)` 取出全部 sessionId 后逐一 `deleteById`，返回删除条数 |
| 前提 | `spring.session.redis.repository-type=indexed` | 没有这个配置就无法按主体名反查会话，只能按 sessionId 单删 |
| 编排 | `AdminUserService.disable` | 先 `user.disable(actor)` 过领域校验（仅管理员 / 不能禁用自己 / 重复禁用报 `ID-2007`），成功后再 `revokeAll`，最后审计 `USER_DISABLED` 并在详情里记 `revokedSessions=N` |

## 后果

- **正面**：禁用接口返回即生效，被禁用者的下一个请求就是未认证；审计里带删除数量，事后可取证；
  端口放在应用层，单测用 `RecordingSessions` 断言「删了谁、删了几次」。
- **负面**：Redis 成了下线链路的硬依赖。Redis 抖动时 `revokeAll` 返回 0，账号状态已改但会话可能活到 TTL，
  需要运维按 `revokedSessions=0` 告警补删。
- **边界**：本地/单测上下文没有启用 Spring Session 时，`ObjectProvider.getIfAvailable()` 返回 `null`，
  `revokeAll` 退化为 0，不影响其他单测；真实链路由 `DisableUserSessionRevocationIT` 覆盖
  （禁用后原 Cookie 请求 `/api/v1/auth/me` 返回 401，管理员自己的会话不受影响）。
- **多实例**：主体名索引与会话都存在 Redis，语义与单实例一致。

## 被否决的替代方案

- **只改 status**：不满足「立即」，且要等 TTL，违规内容还能继续发。
- **JWT + 短 TTL**：ADR-003 已否决 JWT；把 TTL 压到分钟级会带来持续刷新成本，且在 TTL 内仍然有效。
- **会话版本号（`user.sessionEpoch`）**：每次鉴权都要比对版本，改动面覆盖所有安全路径，收益与直接删会话等价。
- **直接按 key 前缀扫 Redis 删除**：绕过 Spring Session 的索引结构，框架升级或改存储时容易失效。

## 验证

| 证据 | 位置 |
| :-- | :-- |
| 单元测试：禁用时调用 `revokeAll`、审计含 `revokedSessions=2`、非管理员/禁用自己时不触发 | `AdminUserServiceTest` |
| 集成测试：禁用后原会话 401、管理员会话仍 200 | `DisableUserSessionRevocationIT` |
| 接口 | `POST /api/v1/admin/users/{id}/disable` |
| 配置 | `application.yml`：`spring.session.redis.repository-type=indexed`、`timeout: 30m` |
